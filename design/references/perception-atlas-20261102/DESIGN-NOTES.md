# 새 레퍼런스 12장 검토 기록

2026-11-02 · [전체 갤러리](index.html) · [연구 근거](RESEARCH.md) · [실제 프롬프트](prompts.json)

## 제작 범위

- 도구: **built-in image_gen**. 새 생성과 이미지 편집을 사용했다. Python이나 코드로 이미지 픽셀을 편집하지 않았다.
- 이전 레퍼런스 이미지는 입력으로 쓰지 않았다. 이번에 새로 만든 기준 화면을 후속 장면에 공유해 같은 제품으로 보이게 했다.
- 초기의 큰 제목·반복 상자 시안은 제외했다. 파일명·메서드 타입·외부 Queue API 소속·선 방향·다크 화면 글자 대비를 대조해 여러 장을 교정했다.
- 선택된 12장 모두 생성 결과를 직접 보며 검토했다. 화면별 프롬프트, 교정 프롬프트, 최종 원본 경로는 prompts.json에 있다.
- 모든 PNG는 **디자인 레퍼런스**다. 실행 중인 EXE 캡처, 실제 Meta 응답·이미지, 구현 완료·실행 검증·사용자 승인의 증거가 아니다.
- 영어 기본, 라이트/다크, 큰 프리뷰, 선택 요소의 구성, 수준별 설명, 파일 분리·통합·검토를 다룬다. Unity/MR을 되살리는 제안이 아니다. 3D 메시 생성은 미연결 목표로 남긴다.

## 공통 시각 체계

큰 프리뷰는 실제 결과물을 보는 프레임으로 표현한다. 소스 구성은 여백 위의 도해로 표현하며 열린 괄호로 소속을 묶는다. 함수는 모서리를 깎은 판, 상태는 원통형 레지스터, 에셋은 이미지 타일을 기본으로 한다. 단어도 함께 표시해 색만으로 의미를 전달하지 않는다.

전체를 밝게 강조하지 않고 현재 선택과 관련 경로에 강한 주황색을 집중시킨다. 설명은 넓게 읽는 면, 파일 작업은 원본과 목적지, 에셋은 큰 이미지 무대, 검토는 전후 코드라는 서로 다른 배치를 갖는다.

생성 이미지가 모든 형태 규칙을 완벽히 지킨 것은 아니다. 실제 구현에서는 동일한 소스 ID와 타입에서 하나의 도형을 결정하고, 선택 안내선·소속·정적 의존 관계를 별도로 렌더링해야 한다. 모든 장면의 화살표를 그대로 코드에 옮기지 않는다.

## 소스 대조 기준

- CheckoutController.cs의 CheckoutController, TotalsView, CartSummary는 같은 파일의 선언이다.
- CouponRules.cs는 CouponRules와 CouponValidator를 포함한다. DiscountPercent는 20이며 CalculateTotal은 subtotal * (1 - DiscountPercent / 100)을 반환한다.
- CartState.cs와 depth.preview.json을 확인했다. 프리뷰 바인딩은 선언된 항목 기준이며 임의 프로젝트 런타임 UI를 자동 발견했다는 뜻이 아니다.
- TaskRunner/JobQueue.cs는 Queue<string> pending을 소유한다. Add(string item), Next()의 string 반환, Count 프로퍼티가 있다. Queue<T>의 Enqueue/Dequeue는 외부 API다.
- TaskRunner의 App.cs에는 Program과 Pricing이 있다. 이미지 생성 중 생긴 가짜 파일·메서드를 가능한 범위에서 제거했다.
- FIFO 그림은 소스 기반 개념 설명이다. 모델의 비공개 사고 과정을 표시하는 것이 아니라 사용자에게 검증 가능한 설계 이유·계약·근거를 보여주는 제안이다.

## 구현에 넘길 때 반드시 바로잡을 점

- 01의 ShopCart와 11의 HomeGoods는 실제 예제명 Checkout으로 통일한다.
- 04의 일부 필드 몸체도 01의 상태 레지스터 규칙으로 통일한다. 일부 장면의 개요 표식은 새 메서드로 인덱싱하지 않는다.
- 05의 CartSummary 설명은 합계를 계산한다는 의미로 고친다. 실제 UI를 갱신하는 모듈로 설명하지 않는다.
- 08의 직사각 표는 전체 인접행렬이 아닌 A의 발췌로 명시한다. B = PᵀAP의 실제 값과 관계는 서비스 데이터로 계산해야 한다.
- 09의 작은 생성 오탈자와 10의 제안 화살표 시작점은 교정이 남아 있다. 실파일 적용 전 복사본 검증과 승인 상태를 명확하게 표시한다.
- 11의 이미지·변형·메타데이터는 디자인 예시다. 실제 생성 결과와 사용처는 서비스 응답을 확인해 표시해야 한다.
- 12의 계산 예시는 테스트 통과 표시로 바꾸지 않는다. 기존 상수 변경의 호환성과 실제 동작을 검증해야 한다.
- 대비·글자 크기·실제 클릭 영역·긴 이름·접근성·모듈이 많은 경우의 배치는 구현 후 실측해야 한다.

남은 오차를 숨기고 정확한 소스 그래프나 실제 검증 결과로 취급하지 않는다. 사용자가 원하는 시각적 차별성에 대한 새로운 제안이며 최종 선호는 아직 확인되지 않았다.
