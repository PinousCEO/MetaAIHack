## 최신 후속 요청 — Unity 오류 수정

사용자가 이 프로젝트의 Unity 오류 수정을 요청했다. 실제 MetaAIHack Editor.log에 `DepthMetaWorkspace.cs(155,23)`의 `UnityWebRequestTexture`, `(158,25)`의 `DownloadHandlerTexture` CS0103이 있었다. 기본 `unitywebrequest`만 있고 `unitywebrequesttexture` 내장 모듈이 빠진 것이 원인이다. manifest/lock에 추가하고 사용자가 새로 설치한 AI Assistant 패키지를 보존했다.

Unity가 생성한 실제 compiler response를 복사해 두 오류를 재현했다. 같은 입력에 누락 DLL 참조만 추가하자 컴파일 성공했다. 근거: `artifacts/unity-error-fix/before.log`, `with-texture-module.log`, `project-input-check.log`. 이전 참조 검증은 설치된 모든 Unity DLL을 포함해 프로젝트의 누락 모듈을 발견하지 못했다. `check-unity-scripts.ps1`을 실제 Unity response 기반으로 바꿨으며 오래된 manifest 입력도 거부한다. 출력은 artifacts에만 쓴다.

ContactShadow/SpatialFloor/Pearl의 첫 줄에 붙어 있던 CGPROGRAM과 마지막 ENDCG를 별도 행으로 분리했다. 실제 로그에 있던 `Unexpected extra tokens/token '-' in #line directive`에 대한 수정이며 재질 수식/색상은 바꾸지 않았다. 아직 실제 shadercompiler 재실행 결과는 없다. MCP 대상은 여전히 WorldVR이며, MetaAIHack Editor가 수정된 패키지를 읽도록 창 활성화를 사용자에게 요청했다. Editor reload·Play Mode·최신 EXE 성공으로 보고하지 않는다.

## 최신 정정 — 현재 Meta Model API 사용

사용자는 제공한 키를 `.env`에 직접 저장하고 프로젝트에 필요한 Meta API를 쓰라고 했다. 키 저장과 Git 제외를 완료했다. **이전의 “Llama 키로 이미지 생성 불가, SAM/Chameleon 필요” 안내는 과거 SDK만 확인한 오류**였다. 현재 공식 문서는 `api.meta.ai/v1`에서 Muse Spark와 Muse Image를 같은 인증으로 제공한다. [정확한 설정/범위](META-MODULES.md)의 최신 정정 절을 우선한다.

- 기본 코드 모델 `muse-spark-1.3`, 이미지 모델 `muse-image-1.0`. `.env` 서버 로딩, UI 공개 설정, 현재 Chat/Muse Image 전송, PNG 검토·승인 import를 연결했다. SAM/Chameleon 기본 UI를 제거하고 과거 코드는 명시적 worker 호환 경로로 보존했다.

- 비밀 값은 API 응답/이력/복사 프로젝트에 넣지 않는다. `.env`를 읽거나 diff에 포함해 키를 노출하지 않는다. 값 없는 `.env.example`만 버전 관리 대상이다.
- **189 assertions**, `artifacts/self-test-model-api.log`; HTTP/MCP 기존 흐름과 Unity 참조 컴파일 통과. Muse 응답은 fixture다. 새 EXE/실제 생성은 미검증이다.
- 사용자 키로 공식 `/models`에 실제 요청했지만 기존 세션 네트워크 연결이 인증 전에 실패했다. 계정/키가 잘못됐다고 단정하지 않는다. `artifacts/meta-api-connection.json` 및 `meta-api-check.json`은 비밀 없는 상태 결과다. 일반 터미널에서는 `scripts/check-meta.ps1`, 작은 추론까지 확인하려면 `-Probe`를 사용한다. 프록시 우회는 하지 않았다.

사용자는 Queue를 사용한 코드라면 FIFO를 풀어 설명하고 실제 사용 이유까지 이해할 수 있어야 하며, 초보자에게는 자세히, 숙련자에게는 간결하게 보여 달라고 요청했다. 상세 구현은 [Meta 모듈 문서](META-MODULES.md)의 설명 수준 절을 따른다.

- 동일한 기록으로 beginner/intermediate/expert 표현을 만든다. 수준 전환은 모델 호출이 없고 근거·주의점이 유지된다. AI 기본 계약은 학습용 장문을 제외한 압축 표현이다. HTTP `/modules/explanation`과 MCP `modules.explanation`은 동일한 응답을 사용한다. 총 12개 MCP 도구다.
- Unity 모듈/Notes/Details에 수준 선택·코드 근거 연결, 선택 저장, Meta 채팅 수준 전달, 선택 모듈만 분석을 추가했다. UI는 참조 컴파일 검증이며 실제 플레이어 화면은 미검증이다.

## 이번 구현

### 변경 줄을 직접 검토

- HTTP/MCP 공통 검토 응답의 각 파일에 줄 diff를 추가했다. 추가/삭제 줄 번호, 분리된 hunk, 주변 3줄, 최종 개행/개행 형식 변경을 구분한다.
- Unity Changes는 기본으로 추가·삭제 색과 줄 번호를 표시하며 전체 파일 보기로 전환할 수 있다. 600줄을 넘으면 생략 수와 전체 파일 진입을 표시한다.
- 중간 비교가 100만 셀을 넘으면 정확한 삭제/추가 블록으로 전환하고 최소 diff가 아님을 표시한다. 이동·의미적 리팩터링 판정이 아니다.

### 대상 프로젝트 빌드·테스트 실행기

- 서비스 저장소에 프로젝트별 명령 profile을 저장한다. 실행 파일, 개별 인수, 상대 작업 폴더, build/test 구분, 1–900초 제한과 적용 전 통과 필수 여부를 지정한다. 최대 8개 명령이다.
- Unity Changes의 `Build & tests`에서 설정하고 `Run validation`으로 실행한다. 가져오기나 MCP 제안은 명령을 자동 실행하지 않는다. 실행 중 취소와 이후 명령 로그 조회를 연결했다. **이 UI는 참조 컴파일만 통과했고 실제 클릭/렌더링은 미검증이다.**
- 원본을 바꾸지 않고 설정·소스·에셋을 복사한 뒤 제안 코드를 복사본에 적용한다. 사용자 지정 명령을 shell 문자열 합성 없이 별도 인수로 실행한다.
- 복사본은 **파일 변경 격리**다. 명령 자체는 호스트 권한과 서비스 환경을 갖는다. 사용자 명령이 절대 경로로 원본을 수정하거나 외부 시스템에 접근하는 것을 막는 OS sandbox가 아니다.
- `.git`, `.depth`, `Library`, `Temp`, `Logs`, `obj`, `bin`, `build`, `artifacts`, `node_modules`, `.dart_tool`을 제외한다. 나머지 링크는 거부한다. 최대 20,000파일/512 MiB이며 의존성 복원이 필요할 수 있다. Git 메타데이터/외부 상위 설정에 의존하는 빌드는 별도 조정이 필요하다.
- 명령별 종료 코드, 시간, stdout/stderr, 실패/미실행/시간 초과/취소를 보존한다. stdout·stderr는 각각 최대 32,000자를 보관하며 넘으면 명시한다. 전체 로그 무제한 보관 기능은 아니다.
- 결과는 프로젝트 ID, 제안 ID/내용, 소스 revision, profile, 복사 입력 manifest와 환경 해시에 연결한다. 환경 값은 기록하지 않는다. csproj 등 인덱스 밖 설정이 바뀌어도 성공 결과를 만료시킨다. 실행 파일/SDK가 같은 경로에서 교체된 경우까지 검출하는 toolchain fingerprint는 후속 작업이다.
- 설정한 명령만 실제 실행 상태로 표시한다. 테스트 명령이 없으면 `Behavior tests`는 계속 `not-run`이다. 필수 검증이 없거나 실패/만료되면 UI를 우회한 Apply도 거부한다. 기본 미설정 프로젝트는 기존 검토/적용 흐름을 유지한다.
- HTTP: `GET/POST /validation/profile`, `POST /proposals/{id}/validate` (`approved:true` 필요), `GET /proposals/{id}/validation`, `POST /proposals/{id}/validation/cancel`. 검증 실행 명령은 MCP 도구로 추가하지 않았다.
- 실행 결과/복사본은 서비스 저장소 `validation/{projectId}/{proposalId}/{runId}`에 남는다. 정리/보존 정책과 profile별 환경 지정은 미구현이다. 후속 변경으로 영속 제안과 중단 복구를 추가했다.

## 후속 요청: 모든 기능의 동작 여부와 추가 구현

사용자는 “원하는 모든 기능이 잘 작동하는 것이 아니라면 멈추지 말고 구현”을 요청했다. **전체 완성은 아니다.** 아래 결과를 MR, 범용 실행 프리뷰, 의미적 코드 재사용·행동 보존까지 완료한 것으로 확대하지 않는다. 최신 검증 로그는 `artifacts/self-test-expanded-v8.log`의 118 assertions다. 실제 플레이어 화면은 여전히 이전 EXE뿐이다.

### 재시작·복구·되돌리기

- 프로젝트별 `pending/{projectId}.json`을 원자적으로 저장한다. 재시작/재가져오기 후 같은 제안 ID와 검토를 복원하고, 다른 프로젝트의 동일 revision과 섞지 않는다. Dismiss도 저장한다.
- Apply 전에 원본 bytes와 이전 분류를 journal에 저장한다. 여러 파일 쓰기 도중 중단되면 재시작 후 감지하고 추가 Apply를 차단한다. `History`에서 원본 복구를 선택할 수 있다. 외부 편집/파일 누락은 충돌로 표시하며 덮어쓰지 않는다. 실제 프로세스 강제 종료 대신 첫 파일만 기록된 상태를 만들어 복구를 검사했다.
- 적용 이력의 `Review undo`는 새 제안이다. 기존 검토·필수 검증·승인·재분석을 통과해야 한다. 이후 소스 변경뿐 아니라 같은 revision의 후속 모듈 분류도 보호한다. 되돌리기는 원본 텍스트 복원이며 원본 인코딩을 보장하는 기능은 아니다. 중단 복구는 BOM을 포함한 원본 bytes를 복원한다.
- `GET /history`, `GET /recovery`, `POST /history/{id}/undo`, `POST /recovery/restore`를 추가했다. 이력은 최신 100개를 제공한다. 외부 편집과 파일시스템 쓰기 사이의 OS 수준 원자성, 충돌의 자동 병합, 보관 정책은 없다.

### 실제 C# 컴파일 입력

사용자가 대상 프로젝트를 restore/build한 뒤 명시적으로 실행한다:

```powershell
dotnet run --project src/Depth.Service -c Release -- --capture-analysis C:/target/root src/App/App.csproj src/Shared/Shared.csproj
```

- `depth.analysis.json`에 compiler source list, define, language version, nullable/unsafe/checked/output options, 해시가 연결된 참조와 설정을 저장한다. 일반 import는 MSBuild를 실행하지 않는다. 캡처 명령은 MSBuild Compile target을 사용하므로 프로젝트 target의 실행이 가능하다.
- 현재 소스를 포함/제외 목록과 define에 맞춰 분석한다. generated global usings 등은 분석 입력이지만 편집 모듈로 만들지 않는다. 캡처된 프로젝트 간 참조는 최신 source compilation으로 연결하므로 빌드 당시 DLL의 오래된 멤버에 바인딩하지 않는다.
- 설정·소스 목록·참조가 바뀌면 명시적으로 recapture 오류를 낸다. 매니페스트가 없으면 source-only라는 진단을 유지한다. 속성 편집과 diff의 C# 구문 매핑에도 같은 parse options를 쓴다.
- 선택한 assembly당 하나의 구성만 지원한다. 여러 assembly가 같은 소스를 컴파일하는 linked-source 구성, 자동 solution 탐색, source generators/analyzers 실행, Unity asmdef 전용 로딩은 지원하지 않는다. SDK/import/환경의 완전한 재현성을 보장하지 않는다.
- 근거: [MSBuild 평가 결과 조회](https://learn.microsoft.com/en-us/visualstudio/msbuild/evaluate-items-and-properties), 설치된 SDK 8.0.419의 `Microsoft.CSharp.Core.targets`.

### Dart와 Web

- Dart는 `AnalysisContextCollection`의 resolved unit/element를 사용한다. 두 파일의 사용처가 같은 구현 ID를 가리키는 것, 필드·생성자 연결, 동적 호출과 동명 무관 함수의 오연결 거부를 실제 analyzer로 검증했다. Flutter 화면 요소/creation location과의 런타임 연결은 없다.
- Web은 `adapters/web/`에서 `npm ci --ignore-scripts`로 고정 TypeScript 5.9.3을 설치한 뒤 `DEPTH_WEB_ADAPTER`를 `index.mjs` 절대 경로로 설정한다. 루트 tsconfig/jsconfig의 include/exclude, paths와 extends를 읽는다. 미설정 시 기본 compiler options를 썼다고 명시한다. 프로젝트 코드/plugin을 실행하거나 emit하지 않는다.
- JS/TS/JSX/TSX 및 mjs/cjs/mts/cts 텍스트를 해시·조회·제안·검토·적용할 수 있다. resolved symbol의 호출/참조/생성/상속과 JSX 컴포넌트 구성을 공통 ID/영향/문맥에 연결한다. Web ID는 파일과 선언 범위를 포함하므로 파일 이동/이름 변경 때 바뀐다.
- Web project references는 별도 루트가 필요하다고 진단한다. Vue/Svelte 템플릿, DOM/React 런타임 선택, 동적 dispatch의 실제 대상, 외부 패키지 전체 fingerprint는 지원하지 않는다. 비-C# 편집의 자체 구문 검사는 계속 `not-run`이다. 지정한 `tsc` 명령은 별도의 Target build 결과다.
- `scripts/run.ps1`은 설치된 Web 어댑터를 발견하면 연결한다. 배포 패키지에 Node/Dart/어댑터 설치를 포함한 것은 아니다.
- 근거: [Dart analyzer API](https://pub.dev/documentation/analyzer/10.1.0/dart_analysis_analysis_context_collection/), [TypeScript compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API).

### UI와 프로젝트 격리

- `Edit.operation`을 `replace/create/delete`로 확장했다. 기존 필드만 보낸 요청은 replace로 호환된다. 새 파일은 비어 있는 expectedHash와 사용하지 않는 소스 경로가 필요하고, 삭제는 기존 해시와 빈 content가 필요하다. `changes.propose`의 schema도 같은 계약이다.
- 생성/삭제를 포함한 diff, 복사본 build/test, 승인 Apply, 중단 복구, 검토형 undo를 구현했다. 경로 별칭 중복·기존 파일 충돌·프로젝트 밖 경로·인덱스 제외 폴더를 거부한다. 외부 편집된 생성 파일을 복구가 삭제하지 않는다. 생성 과정의 빈 폴더는 undo 이후 남을 수 있다.
- Module library의 `New source`, 소스 편집의 삭제 선택으로 요청할 수 있다. 빈 프로젝트의 첫 파일도 기존 모듈 선택 없이 검토할 수 있도록 연결했다. UI 렌더링은 아직 검증하지 못했다.
- **제한:** 생성/삭제는 지원 언어의 소스 파일만 대상으로 한다. csproj/asset 수정, 패키지 통합, 의미적 import 갱신, Unity `.meta` GUID 이동은 구현하지 않았다. `depth.analysis.json`이 활성화된 C#의 source inventory 변경은 거부한다. 그런 작업은 source-only 분석으로 전환해 검토·검증·적용한 후 컴파일 입력을 다시 캡처해야 한다.
- 실제 C# fixture에서 공유 구현 파일 생성 + 호출부 교체 + 이전 파일 삭제를 복사본에서 빌드/실행하고, 적용·재분석·중단 복구·검증형 undo를 확인했다. Web HTTP 검사도 새 rate 파일 생성/불필요한 파일 삭제/기존 import 변경을 포함한다. 특정 시나리오의 성공이며 범용 자동 재구성이나 행동 보존 증명이 아니다.

- Code 탭의 `Edit full source files`에서 전체 파일을 수정해 기존 변경 검토로 보낸다. 즉시 원본에 쓰지 않는다. 새 파일 생성·삭제도 검토에 연결했다. 의미적 이동과 import/asset GUID 자동 갱신은 아직 없다.
- 현재 공간뷰가 `/runtime/selection`을 읽지 않던 누락을 수정했다. Unity bridge가 관찰한 컴포넌트 소스의 후보 모듈을 공간에서 모으고, `Runtime selection`에서 따라가기와 개별 후보 탐색을 제공한다. 실제 실행 함수를 확정한 것으로 표시하지 않는다. UI 편집 중에는 자동 전환하지 않는다.
- API 응답 전후와 도구 호출 시 시작 프로젝트/revision을 다시 검사한다. CLI의 MCP도 `--project-id ... --revision ...`에 고정된다. 오래된 작업으로 다른 프로젝트를 조회·변경 제안하지 않는다. `changes.propose`는 `projectId`를 요구한다.
- **이력/소스 편집/런타임 선택 UI는 Unity 참조 컴파일만 통과했다.** 실제 EXE 상호작용·렌더링 검증은 아직 불가하다.
