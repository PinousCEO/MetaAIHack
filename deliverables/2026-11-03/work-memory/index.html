무엇을 했는가
“3개 파일 수정”에 그치지 않습니다. 추가된 함수, 바뀐 책임, 새 호출 관계, 삭제된 연결, 영향을 받을 사용 지점을 보여줍니다. 작업을 누르면 그 시점의 전후 그래프로 이동합니다.


왜 그렇게 했는가
요구사항 → 선택한 설계 → 대안과 비용 → 유지할 조건 → 검증 결과를 연결합니다. 초보자는 Queue와 FIFO부터, 숙련자는 순서 보장·실패 처리·동시성 제약부터 읽습니다. 같은 근거를 깊이만 다르게 설명합니다.


지금 어디까지 진행됐는가
작업 중, 파일 감지, 분석 중, 설명 대기, 설명 실패, 검증 실패를 분리합니다. 파일을 저장하면 그래프부터 갱신하고 Meta 응답을 기다리며 멈추지 않습니다. 테스트를 실행하지 않았다면 그대로 표시합니다.


이전에 왜 이렇게 만들었는가
모듈마다 생성 작업, 이후 변경, 설계 결정, 제약, 근거 소스, 현재 유효 여부가 연결됩니다. 새 CLI는 작업에 필요한 기록부터 읽고, 의문이 있는 부분의 원본 코드만 추가로 확인합니다.





실시간 갱신과 작업 출처


연결만으로 CLI의 모든 셸 작업을 볼 수 있다고 가정하지 않습니다. MCP 도구는 클라이언트가 호출하는 인터페이스입니다. Depth Lens에서는 별도 CLI 어댑터가 작업 시작·종료·검증 결과를 보고하고, 파일 감시기가 실제 변경을 확인하도록 설계합니다. 이는 MCP Tools 명세를 바탕으로 선택한 제품 구조입니다.


관찰 수단알 수 있는 것표시 규칙


CLI hooks / 작업 보고 도구세션·작업 ID, 명시한 목표와 설계 이유, 도구·실행 결과“CLI가 보고함”. 성공 보고만으로 실제 파일·테스트 검증이 되지는 않음


파일 감시 + 해시 + 소스 분석생성·수정·삭제, 선언과 의존성 변화“파일에서 확인”. 행위자가 불분명하면 “외부 변경 · 작업자 미확인”


승인된 검증 실행기실행 명령, exit code, 로그 해시, 대상 revision직접 관찰한 결과만 “실행 확인”. 다른 프로세스의 보고는 별도


Meta 설명 작업요구사항과 소스 변화의 의미, 설계 선택의 이유와 비용명시된 의도와 AI 해석을 분리. 모델명·입력 revision·근거 ID 보관




저장 이벤트는 짧게 묶어 재분석하고, 삭제·이동·임시 구문 오류를 처리합니다. 감시 이벤트가 누락되거나 앱을 재시작하면 디렉터리 스냅샷과 해시를 대조합니다. Git이 없는 폴더도 지원하는 설계이며, 파일 시각만으로 여러 CLI 중 누가 썼는지 단정하지 않습니다.


노드 위치와 사용자가 펼친 영역을 유지합니다. 새 연결은 짧게 강조하고, 삭제된 관계는 해당 작업의 전후 보기에서 확인합니다. 변경마다 화면 전체를 재배치하거나 선택을 빼앗지 않습니다. 사용자가 과거 작업을 보고 있다면 현재 변경은 배지로 알립니다. 모션 줄이기 설정을 따릅니다.



Meta가 설명할 근거


설명 입력은 사용자가 요청한 목적, CLI가 명시적으로 남긴 설계 메모, 실제 diff, 관련 모듈의 계약과 의존성, 검증 결과입니다. Meta의 역할은 이 자료를 읽고 사용자가 이해할 설명과 구조화된 결정을 작성하는 것입니다. 파서가 관계를 찾고, Meta가 그 의미를 설명합니다. 이 새 방향에서도 설명 공급자는 Meta로 정합니다. 모델 ID는 실제 연결 검증 뒤 기록하며 다른 공급자로 조용히 바꾸지 않습니다.


종류예시기록 방식


확인된 사실enqueue는 뒤에 추가하고 drain은 앞에서 꺼낸다.소스 파일·심볼·줄·해시 및 근거 ID


보고된 목적CLI가 “접수 순서대로 저장 요청을 보내기 위해”라고 설명했다.세션·작업 ID와 명시적인 목적 문장


Meta의 설계 해석동시 저장보다 직렬 소비가 호출 순서를 유지하기 쉽다.해석임을 표시하고 근거·전제·대안을 연결


알 수 없음왜 LinkedList 대신 배열을 선택했는가?기록이 없다면 “선택 이유 미기록”. 가능한 이유를 실제 의도로 바꾸지 않음




모델 내부 사고 과정을 저장하는 기능으로 정의하지 않습니다. 사용자가 검토할 수 있는 설계 이유·요약·근거를 저장합니다. 단순히 Queue를 썼다는 이유로 “네트워크 저장 성공 순서 보장”을 주장하지 않으며, 실패·재시도·서버 처리 조건을 별도로 설명해야 합니다.



다음 CLI가 읽는 프로젝트 기억


기준 데이터는 버전이 있는 JSON입니다. 같은 데이터에서 사람용 문서를 만듭니다. 긴 자연어 설명을 매번 모두 넣는 대신 프로젝트 개요 → 관련 모듈 → 설계 결정 → 필요한 소스 순서로 가져옵니다. 자동으로 읽게 하려면 CLI의 시작·작업 hooks 또는 명시적인 시작 지침도 연결해야 합니다. MCP 서버 연결 자체가 문서 사용을 강제하지는 않습니다.


기록핵심 내용역할


Project snapshotprojectId, revision, 분석 범위, 모듈·연결, 미해석 관계현재 구조. revision은 소스 해시 manifest에서 계산


Action journaleventId, actionId, sessionId, 순번, 관찰 출처, 전후 revision, 결과추가 방식으로 이력 보관. 중복 이벤트는 eventId로 제거


Module contract책임, 입력·출력, 의존성, 불변 조건, 부작용, 근거원본 전체를 읽기 전 모듈 이해. 경로와 줄 번호만으로 ID를 만들지 않음


Decision record요구사항, 선택, 이유, 대안, 비용, 전제, 근거 ID, 작성 주체왜 그렇게 만들어졌는지 보존. 해석과 보고된 의도 분리


Context packet질의, 기준 revision, 관련 모듈·결정·영향 경로, 한계, 생략량다음 CLI가 필요한 부분만 읽는 제한된 묶음




설명은 단순한 파일 수정 시간 대신 참조한 소스·관계·설정의 fingerprint에 묶습니다. 그 입력이 바뀌면 이전 설명은 이력에 남기되 현재 판단의 근거로 반환하지 않습니다. 재분석 중에는 기존 revision의 스냅샷과 현재 파일 상태를 구분합니다. 재시작 후에도 마지막 이벤트 순번에서 복구하고, 충돌하는 작업은 하나의 원인으로 합치지 않습니다.


작업 공간의 기본 저장 후보는 .depth-lens/입니다. events.jsonl은 사건, snapshots/는 구조, modules/와 decisions/는 설명, index.json은 탐색 진입점입니다. 이 경로는 감시 대상에서 제외합니다. 읽기 전용 폴더에는 사용자 데이터 경로에 저장하고 문서 내 경로는 프로젝트 상대 경로로 유지합니다. 비밀 파일·원시 환경 변수·전체 셸 출력은 자동 수집하지 않습니다.



MCP 인터페이스 초안


제품 도구 이름응답 / 동작


lens.project_overview프로젝트 구조, 최신 revision, 분석 범위와 문서 갱신 상태


lens.context_gettask / moduleIds / expectedRevision / maxCharacters에 맞는 문맥. 생략된 ID·추가 조회 경로 명시


lens.module_get계약, 방향과 종류가 있는 인접 관계, 소스 근거, 설명


lens.action_get특정 작업의 전후 변화, 이유, 검증 상태, 영향 후보


lens.changes_sincecursor 이후 변경. 재시작·이벤트 공백이면 재동기화 지시


lens.action_reportCLI가 시작·완료·실패·취소와 명시적 목적을 보고. 소스 편집·셸 실행 권한은 없음




depth-lens://projects/{projectId}/overview와 revision별 모듈·작업 resources도 제공합니다. 구독을 지원하는 클라이언트에는 자원 갱신을 알리고 클라이언트가 다시 읽습니다. 미지원 클라이언트는 lens.changes_since로 조회합니다. 갱신 통지는 파일 변경을 CLI에서 수집하는 기능과 별개입니다. 구독은 MCP Resources 명세의 선택 기능입니다.


응답은 MCP structuredContent와 호환 텍스트를 함께 제공하는 설계입니다. 위 도구 이름·URI·이벤트는 Depth Lens의 초안이며 MCP 표준 도구나 현재 배포된 서버를 뜻하지 않습니다. 길이 제한은 문자 수로 명시하고 토큰 수로 바꿔 부르지 않습니다. 실제 읽힌 리소스도 모든 CLI에서 확인할 수 있는 것은 아닙니다.



첫 구현의 수용 조건


    

  1. JS/TS 샘플 프로젝트를 CLI가 생성·수정·삭제하면 새 노드·관계와 작업 ID가 일치한다. 시작 목표는 파일이 안정된 뒤 작은 프로젝트에서 그래프 갱신 p95 1초 이내이며, 측정 전 달성값으로 표시하지 않는다.
    2. 

  2. 편집, 조회, 테스트, 실패, 취소를 구별한다. 조회·테스트만 한 작업은 그래프 변화가 없어도 기록한다. 이벤트 중복·역순·CLI 비정상 종료 후 이력이 보존된다.
    3. 

  3. Meta 지연·오류에도 구조도는 갱신된다. 같은 입력 fingerprint의 설명은 재사용하고, 설명 대기·실패·이전 버전을 명시한다.
    4. 

  4. 두 CLI가 동시에 파일을 고친 경우 원인 확인이 안 된 변경을 임의로 귀속하지 않는다. hooks가 없는 CLI는 파일 관찰 범위만 제공한다.
    5. 

  5. 새 MCP 세션이 요약과 관련 문맥으로 예시 작업을 이어간다. 받은 모듈 ID·소스 revision·근거를 실제 파일과 대조하며, 문서가 틀렸거나 누락되면 원본을 조회한다.
    6. 

  6. 문서에 포함된 지시문은 프로젝트 데이터로 취급한다. 임의 경로 탈출, 비밀 파일 유입, 오래된 근거, 미실행 테스트를 성공으로 표기하는 응답을 거부한다.
    7. 

  7. 실제 Windows 투명 창에서 여러 배경·DPI·모니터·클릭 통과 복구·가독성을 별도로 검수한다. HTML 시뮬레이션을 OS 검수로 대체하지 않는다.
    8. 



지금 만들어 둔 것과 다음 구현


이번에는 승인한 12장의 시각 방향에 이 기능 요구와 데이터 계약을 추가했습니다. 기계용 연결·기록 계약, 해시와 소스가 포함된 예제 기록, 위 단계별 시뮬레이션을 함께 제공합니다. 실제 Meta 호출과 새 MCP 서버는 아직 연결하지 않았습니다.


기존 보관 코드의 McpBridge.cs에는 도구 조회·호출이 있고, ModuleKnowledge.cs에는 소스 fingerprint에 연결된 설명과 간결한 모듈 계약이 있습니다. 재사용 후보입니다. 새 요구의 작업 이벤트 수집, 지속적인 journal, resource 갱신, 새 투명 패널은 별도 구현 대상입니다. 이전 제품의 임의 런타임·MR 작업을 다시 시작하지 않습니다.


샘플은 설명용으로 작성한 데이터입니다. 코드 해시는 동봉한 샘플 텍스트에서 계산했으며 실제 사용자 프로젝트·Meta 출력·테스트 성공을 나타내지 않습니다. 검사 기록
